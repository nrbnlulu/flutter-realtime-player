# Android GPU video

The experimental Android output samples MediaCodec hardware buffers directly in
Impeller. Playbin and WSC-RTP share the same sample callback and output selection.
The GPU branch does not map decoded pixels, upload RGBA, or allocate an
intermediate video render target. Its Flutter texture ID survives size changes.

This implementation requires changes in both this package and the Flutter Rust
shell fork. H.264 playback, session replacement, and background/resume were
verified on an Armor 21 (Android API 36, Mali-G57 MC2) on 2026-10-29. The original
GStreamer 1.28.3 SDK remains available for CPU fallback; a separate development
SDK was built for the hardware-buffer tests.

## Requirements

- The FlutterActivity Rust runtime (`flutter-shell-android`) with the new
  `GpuTextures::create_android_hardware_buffer_texture` capability.
- Engine and Rust runtime rebuilt together for private shell ABI 13. Mixing the
  updated Rust SDK with an older engine is unsupported.
- A runner generated by rlutter version marker 8 or newer. Its Android library
  has `DF_1_GLOBAL` visibility so FRB's process lookup and GStreamer's runtime
  providers can find the plugin symbols.
- Flutter's normal Java plugin registration before Rust plugin registration.
  This package's Java plugin captures the VM and application class loader; its
  Gradle module reuses the androidmedia Java helpers from the selected SDK.
  Export `GSTREAMER_ROOT_ANDROID` for Gradle as well as configuring Cargo.
- A GStreamer Android SDK containing the forthcoming 1.30 AHardwareBuffer API,
  or a compatible backport of the androidmedia ImageReader output, allocator
  query, and `AHARDWARE_BUFFER` video format. The public header is
  `gst/allocators/gstahardwarebuffer.h`; the query is
  `gst_ahardware_buffer_memory_peek_buffer`.
- A MediaCodec decoder supporting the source codec and hardware-buffer output.
  Start device validation with arm64 SDR H.264.

The build script detects the SDK header. SDKs without it compile only CPU
output, with no references to the new allocator symbol. The existing static
`gstandroidmedia`, `gstallocators-1.0`, and `gstgl-1.0` linkage is reused.

The relevant upstream contracts are in
[the allocator header](https://github.com/GStreamer/gstreamer/blob/main/subprojects/gst-plugins-base/gst-libs/gst/allocators/gstahardwarebuffer.h)
and [androidmedia's image lease](https://github.com/GStreamer/gstreamer/blob/main/subprojects/gst-plugins-bad/sys/androidmedia/gstamcaimagememory.c).
The latter currently waits for the acquire fence before publishing memory. If
that changes to asynchronous fences, this adapter must propagate those fences
before it can safely consume the new output. It accepts only that allocator.

## Ownership and fallback

The decoder negotiates:

```text
video/x-raw(memory:AHardwareBuffer),format=AHARDWARE_BUFFER
```

A `GstBuffer` retains the decoder's AImage lease. The shell's mailbox keeps one
pending frame, replacing it with the latest arrival, and bounds outstanding
leases. Notifications are coalesced while the platform thread is busy. A full
mailbox drops the incoming decoded frame.

The C++ adapter reuses Impeller's `AHBTextureSourceVK`, including native YUV
sampling. It acquires foreign-queue ownership on the shared queue. Impeller's
existing command tracking retains the imported source through GPU reads; the
final source release submits the foreign ownership transfer back and keeps the
GStreamer lease until that transfer completes. Frame tokens remain valid after
texture unregistration and do not dereference the registration's user data.

Crop rectangles and androidmedia's padding/crop transforms are supported.
Arbitrary rotations and shears fall back to CPU output. Protected content and
HDR are outside this initial implementation's validation scope. Device checks
must verify SDR color range and conversion as well as image orientation.

Missing shell capabilities select the existing CPU sink. GPU setup,
negotiation, sample, and import failures retry with CPU output. WSC-RTP retains
its transport reconnect policy and retries output failures once with CPU even
when transport auto-restart is disabled. Every pipeline run has a shared guard
that stops decoder callbacks on early exit or cancellation.

URI and RTP playback share pipeline-clock synchronization, a 100 ms lateness
limit, QoS, bounded appsink buffering, and sample/error handling. Without clock
synchronization the file demo previously decoded twenty seconds of video in
about two seconds. Android static registration uses GStreamer's actual `void`
register-function signatures and includes MP4 and Matroska/WebM demuxers.

No public Dart/FRB API changed, and no native handles cross FRB.

## Device results

| Check | Result |
| --- | --- |
| Playbin, SDR H.264, 640×360 at 30 fps | Moving video observed through `memory:AHardwareBuffer`; twenty-second clip completed in twenty seconds; no CPU fallback |
| GPU session replacement | Four sessions played, including replacement during playback |
| Background/resume | Playback resumed in the same session and texture ID |
| GStreamer 1.28.3 CPU output | Moving video observed; logs confirmed `CPU RGBA` |
| YUV sampler feature | Initial Vulkan feature error fixed; absent in the subsequent GPU run |
| Depth/stencil synchronization | GPU run exposed late-fragment attachment-write hazards; the shared Impeller render-pass dependency was corrected and the engine rebuilt; final on-device validation is pending |
| WSC-RTP | Development-SDK APK built against the local server configuration; not run before the device disconnected |

Screenshots and app-only logs are under `example/build/android-gpu-probe/`
(ignored build output). `gpu-frame-1.png` and `gpu-frame-2.png` show advancing
video timestamps with the same Flutter texture ID. `gpu-resumed.png` and
`gpu-restarted.png` cover lifecycle checks; `cpu-frame-*.png` cover fallback.
These are functional checks, not a CPU/latency/FPS benchmark.

The device disconnected before the APK containing the stencil synchronization
fix and WSC-RTP configuration could be installed. Do not interpret the passing
playback checks as a clean final Vulkan-validation result.

## Repeat the probe

The example entrypoint `lib/android_render_probe.dart` uses the public controller
and player widget. Its restart button disposes the current session before
creating another. It accepts `PROBE_VIDEO_URL` for Playbin or `PROBE_SOURCE_ID`
and `PROBE_BASE_URL` for WSC-RTP. WSC-RTP uses WebSocket transport so ADB reverse
works without a separate UDP route.

On this machine the development SDK is at
`/home/dev/.cache/realtime-player-gstreamer/sdk`. It contains newly built
GStreamer core/base/androidmedia components (pkg-config version `1.29.2.1`) over
a copy of the 1.28.3 dependency SDK. The original SDK was not modified. The source
archive is cached beside it as `gstreamer-main.tar.gz`, SHA-256
`fbd116a9a5f691628f5bb9b0b13fffdf81d1038dbe5b6983b234a7bdca2cfd57`;
`configure.py`, `android-arm64.ini`, and the Meson build directory preserve the
build configuration.

From the example directory, with the local fork's rlutter on PATH:

```sh
export GSTREAMER_ROOT_ANDROID="$HOME/.cache/realtime-player-gstreamer/sdk"
export PKG_CONFIG_LIBDIR_aarch64_linux_android="$GSTREAMER_ROOT_ANDROID/arm64/lib/pkgconfig"
adb reverse tcp:8765 tcp:8765
adb reverse tcp:8000 tcp:8000
rlutter --flutter-root /home/dev/Desktop/oss/flutter \
  --local-engine-src /home/dev/Desktop/oss/flutter/engine/src \
  build android --debug --target lib/android_render_probe.dart
```

The default probe URI is `http://127.0.0.1:8765/demo.mp4`. The test video was
created with `ffmpeg -f lavfi -i testsrc2=size=640x360:rate=30 -t 20 -an -c:v libx264
-preset ultrafast -pix_fmt yuv420p -profile:v baseline -movflags +faststart demo.mp4`
and served from the fixtures directory with `python -m http.server 8765 --bind
127.0.0.1`. For the local media server, add
`--dart-define=PROBE_SOURCE_ID=<running-source-id>`; the base URL defaults to
`http://127.0.0.1:8000/media`.

The locally rebuilt CLI is
`/home/dev/Desktop/oss/flutter/engine/src/flutter/shell/platform/rust/rlutter/target/release/rlutter`.
Use it until the installed CLI has been updated, so the generated runner includes
the Android symbol-visibility fix.

## Checks and remaining work

```sh
cargo test --manifest-path example/runner-rs/Cargo.toml -p flutter_realtime_player --lib
cargo check --lib --manifest-path example/runner-rs/Cargo.toml --target aarch64-linux-android
```

The player has seven passing Rust tests. Shell SDK/ABI/mailbox/texture-ring tests
and 99 rlutter tests also pass; four existing manual Vulkan upload tests remain
ignored. Android Java compilation, APK builds, and the engine rebuild passed.
The Dart probe analyzer reports the fork's Material import deprecation, with no
errors. No FRB binding regeneration was needed because the public API is unchanged.

Remaining checks are the final Vulkan validation run, WSC-RTP playback,
seek/reconnect and dynamic size changes, SDR color-range verification, performance
comparison, and a second GPU vendor. HDR and protected content remain outside
this implementation's validation scope.
